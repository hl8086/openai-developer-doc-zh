
### 如何在使用 LLM 时最大化正确性和一致行为

优化 LLM 是困难的。

我们与许多初创公司和企业的开发者合作过，优化之所以困难，始终归结为以下原因：

*   不知道**如何开始**优化准确性
*   **何时使用什么**优化方法
*   什么水平的准确性对于生产环境来说**足够好**

本文提供了一个关于如何优化 LLM 准确性和行为的思维模型。我们将探讨提示工程、检索增强生成（RAG）和微调等方法。我们还将重点介绍如何以及何时使用每种技术，并分享一些常见陷阱。

在阅读过程中，重要的是将这些原则与您特定用例中准确性的含义联系起来。这看起来可能很明显，但生成需要人工修复的糟糕文案与退还客户 1000 美元而不是 100 美元之间是有区别的。在进入任何关于 LLM 准确性的讨论之前，您应该大致了解 LLM 失败会给您带来多少成本，以及成功会为您节省或赚取多少——这将在最后重新讨论，届时我们将介绍对于生产环境来说多少准确性是"足够好"的。

## LLM 优化背景

许多关于优化的"操作指南"将其描绘为简单的线性流程——你从提示工程开始，然后转向检索增强生成，再到微调。然而，实际情况往往并非如此——这些都是解决不同问题的杠杆，要朝正确的方向优化，你需要拉动正确的杠杆。

将 LLM 优化框架化为更像一个矩阵是有用的：

![Accuracy mental model diagram](https://cdn.openai.com/API/docs/images/diagram-optimizing-accuracy-01.png)

典型的 LLM 任务将从左下角的提示工程开始，在那里我们测试、学习和评估以获得基线。一旦我们审查了这些基线示例并评估了它们不正确的原因，我们就可以拉动我们的杠杆之一：

*   **上下文优化：** 当以下情况时你需要优化上下文：1）模型缺乏上下文知识，因为它不在训练集中，2）其知识已过时，或 3）它需要专有信息的知识。这个轴最大化**响应准确性**。
*   **LLM 优化：** 当以下情况时你需要优化 LLM：1）模型产生格式不正确的不一致结果，2）语气或说话风格不正确，或 3）推理没有被一致地遵循。这个轴最大化**行为一致性**。

实际上，这变成了一系列优化步骤，我们评估、假设如何优化、应用它、评估，然后重新评估下一步。以下是一个相当典型的优化流程示例：

![Accuracy mental model journey diagram](https://cdn.openai.com/API/docs/images/diagram-optimizing-accuracy-02.png)

在这个示例中，我们做了以下事情：

*   从一个提示开始，然后评估其性能
*   添加静态少样本示例，这应该提高结果的一致性
*   添加检索步骤，使少样本示例根据问题动态引入——这通过确保每个输入的相关上下文来提升性能
*   准备 50+ 个示例的数据集并微调模型以增加一致性
*   调整检索并添加事实核查步骤以发现幻觉，从而实现更高的准确性
*   使用包含增强 RAG 输入的新训练示例重新训练微调模型

这是一个针对棘手业务问题的相当典型的优化管道——它帮助我们决定是需要更多相关上下文还是需要模型更一致的行为。一旦我们做出决定，我们就知道作为优化的第一步应该拉动哪个杠杆。

现在我们有了思维模型，让我们深入了解在所有这些领域采取行动的方法。我们将从左下角的提示工程开始。

### 提示工程

提示工程通常是最好的起点。对于摘要、翻译和代码生成等用例，零样本方法通常可以达到生产级别的准确性和一致性，因此它往往是唯一需要的方法。

这是因为它迫使你定义准确性对你的用例意味着什么——你从最基本的层面开始提供输入，所以你需要能够判断输出是否符合你的期望。如果不是你想要的，那么**为什么**不是的原因将告诉你应该使用什么来推动进一步的优化。

为此，你应该始终从一个简单的提示和一个预期的输出开始，然后通过添加**上下文**、**指令**或**示例**来优化提示，直到它给出你想要的结果。

### 评估

这就是为什么**一个好的提示加上一组评估问题和标准答案**是这个阶段的最佳输出。如果我们有一组 20+ 个问题和答案，并且我们已经深入研究了失败的细节并对它们发生的原因有了假设，那么我们就有了正确的基线来采用更高级的优化方法。

在你转向更复杂的优化方法之前，也值得考虑如何自动化这个评估以加速你的迭代。我们看到的一些有效的常见做法是：

*   使用 [ROUGE](https://aclanthology.org/W04-1013/) 或 [BERTScore](https://arxiv.org/abs/1904.09675) 等方法来提供粗略判断。这与人类评审者的相关性不是很高，但可以快速有效地衡量一次迭代对模型输出的改变程度。
*   使用 [GPT-4](https://arxiv.org/pdf/2303.16634.pdf) 作为评估器，如 G-Eval 论文中所述，你向 LLM 提供评分卡以尽可能客观地评估输出。

如果你想深入了解这些内容，请查看[这个 cookbook]( https://cdn.openai.com/API/docs/cookbook/examples/evaluation/how_to_eval_abstractive_summarization)，它将带你在实践中了解所有这些方法。

## 理解工具

所以你已经做了提示工程，你有了评估集，但你的模型仍然没有做你需要它做的事情。最重要的下一步是诊断它在哪里失败，以及什么工具最适合改进它。

以下是一个基本框架：

![Classifying memory problem diagram](https://cdn.openai.com/API/docs/images/diagram-optimizing-accuracy-03.png)

你可以将每个失败的评估问题框架化为**上下文内**或**已学习**的记忆问题。作为类比，想象你在参加考试。有两种方式可以确保你得到正确答案：

*   你在过去 6 个月里上课，在那里你看到了许多关于特定概念如何工作的重复示例。这是**已学习**的记忆——你通过向 LLM 展示提示和你期望的响应的示例来解决这个问题，模型从中学习。
*   你带着教科书，可以查找正确的信息来回答问题。这是**上下文内**记忆——我们通过将相关信息填充到上下文窗口中来解决 LLM 中的这个问题，要么以静态方式使用提示工程，要么以工业化方式使用 RAG。

这两种优化方法是**叠加的，而非排斥的**——它们可以堆叠，某些用例将要求你同时使用它们以获得最佳性能。

让我们假设我们面临的是短期记忆问题——为此我们将使用 RAG 来解决。

### 检索增强生成（RAG）

RAG 是在生成答案之前**检索**内容来**增强**你的 LLM 提示的过程。它用于给模型**访问特定领域上下文**以解决任务。

RAG 是提高 LLM 准确性和一致性的极其有价值的工具——我们在 OpenAI 最大的客户部署中，许多仅使用提示工程和 RAG 就完成了。

![RAG diagram](https://cdn.openai.com/API/docs/images/diagram-optimizing-accuracy-04.png)

在这个示例中，我们嵌入了一个统计数据知识库。当用户提问时，我们嵌入该问题并从知识库中检索最相关的内容。这些内容呈现给模型，模型据此回答问题。

RAG 应用引入了一个我们需要优化的新轴，即检索。为了使我们的 RAG 工作，我们需要给模型正确的上下文，然后评估模型是否正确回答。我将在这里用一个网格来展示一种简单的 RAG 评估思考方式：

![RAG evaluation diagram](https://cdn.openai.com/API/docs/images/diagram-optimizing-accuracy-05.png)

你的 RAG 应用可能在两个方面出现问题：

| 领域 | 问题 | 解决方案 |
| --- | --- | --- |
| 检索 | 你可能提供了错误的上下文，使模型不可能回答，或者你可能提供了太多不相关的上下文，淹没了真实信息并导致幻觉。 | 优化你的检索，可以包括：  \- 调整搜索以返回正确的结果。  \- 调整搜索以减少噪音。  \- 在每个检索结果中提供更多信息  这些只是示例，因为调整 RAG 性能本身就是一个行业，像 LlamaIndex 和 LangChain 这样的库提供了许多调整方法。 |
| LLM | 模型也可能获得正确的上下文但做了错误的事情。 | 通过改进模型使用的指令和方法进行提示工程，如果展示示例能提高准确性，则添加微调 |

这里要记住的关键是，原则与我们开头的思维模型保持一致——你通过评估来找出问题所在，并采取优化步骤来修复它。RAG 的唯一区别是你现在有了检索轴需要考虑。

虽然有用，但 RAG 只解决了我们的上下文内学习问题——对于许多用例，问题将是确保 LLM 能够学习一个任务，以便它能够一致且可靠地执行。对于这个问题，我们转向微调。

### 微调

为了解决已学习的记忆问题，许多开发者会在较小的、特定领域的数据集上继续 LLM 的训练过程，以针对特定任务进行优化。这个过程被称为**微调**。

微调通常出于以下两个原因之一：

*   **提高模型在特定任务上的准确性：** 在特定任务数据上训练模型，通过展示许多正确执行该任务的示例来解决已学习的记忆问题。
*   **提高模型效率：** 用更少的 token 或使用更小的模型达到相同的准确性。

微调过程从准备训练示例数据集开始——这是最关键的步骤，因为你的微调示例必须准确代表模型在现实世界中将看到的内容。

许多客户使用一种称为**提示烘焙**的过程，在试点期间广泛记录提示输入和输出。这些日志可以被修剪成一个包含真实示例的有效训练集。

![Fine-tuning process diagram](https://cdn.openai.com/API/docs/images/diagram-optimizing-accuracy-06.png)

一旦你有了这个干净的集合，你可以通过执行**训练**运行来训练微调模型——根据你用于训练的平台或框架，你可能有可以调整的超参数，类似于任何其他机器学习模型。我们始终建议保留一个留出集用于训练后的**评估**以检测过拟合。有关如何构建良好训练集的提示，你可以查看我们微调文档中的[指导](/guides/fine-tuning#analyzing-your-fine-tuned-model)。训练完成后，新的微调模型即可用于推理。

对于优化微调，我们将重点关注我们在 OpenAI 模型定制产品中观察到的最佳实践，但这些原则应该适用于其他提供商和开源产品。这里需要遵循的关键实践是：

*   **从提示工程开始：** 从提示工程中获得一个可靠的评估集，你可以将其用作基线。这允许一种低投入的方法，直到你对基础提示有信心。
*   **从小处开始，注重质量：** 在基础模型之上进行微调时，训练数据的质量比数量更重要。从 50+ 个示例开始，评估，然后如果你还没有达到准确性需求，并且导致错误答案的问题是由于一致性/行为而不是上下文，则增加训练集大小。
*   **确保你的示例具有代表性：** 我们看到的最常见陷阱之一是非代表性的训练数据，其中用于微调的示例在格式或形式上与 LLM 在生产中看到的内容有细微差异。例如，如果你有一个 RAG 应用，请使用包含 RAG 示例的数据来微调模型，这样它就不会在零样本情况下学习如何使用上下文。

### 综合运用

这些技术可以相互叠加——如果你的早期评估显示上下文和行为都有问题，那么你的生产解决方案很可能最终会使用微调 + RAG。这是可以的——它们叠加使用可以平衡两种方法的弱点。一些主要好处是：

*   使用微调来**最小化**提示工程使用的 token，因为你用许多训练示例替代指令和少样本示例，将一致的行为根植于模型中。
*   使用广泛的微调来**教授复杂行为**
*   使用 RAG 来**注入上下文**、更新的内容或你的用例所需的任何其他专业上下文

使用这些工具改进语言翻译

我们将继续构建上面使用的冰岛语纠正示例。我们将测试以下方法：

*   我们最初的假设是这是一个行为优化问题，所以我们的第一步将是微调模型。我们将在这里尝试 gpt-3.5-turbo 和 gpt-4。
*   我们还将尝试 RAG——在这种情况下，我们的假设是相关示例可能提供额外的上下文来帮助模型解决问题，但这是一个较低置信度的优化。

#### 微调

为了针对我们的用例进行微调，我们将使用一个包含 1000 个示例的数据集，类似于上面的少样本示例：

```
# One training example
SYSTEM: The following sentences contain Icelandic sentences which may include errors. Please correct these errors using as few word changes as possible.
USER: "Hið sameinaða fyrirtæki verður einn af stærstu bílaframleiðendum í heiminum."
ASSISTANT: "Hið sameinaða fyrirtæki verður einn af stærstu bílaframleiðendum heims."
```

我们使用这 1000 个示例来训练 gpt-3.5-turbo 和 gpt-4 微调模型，并在验证集上重新运行评估。这证实了我们的假设——两者都获得了有意义的性能提升，甚至 3.5 模型也比少样本 gpt-4 高出 8 分：

| 运行 | 方法 | Bleu 分数 |
| --- | --- | --- |
| 1 | gpt-4 零样本 | 62 |
| 2 | gpt-4 加 3 个少样本示例 | 70 |
| 3 | gpt-3.5-turbo 使用 1000 个示例微调 | 78 |
| 4 | gpt-4 使用 1000 个示例微调 | 87 |

很好，这开始看起来像是我们用例的生产级准确性了。然而，让我们测试一下是否可以通过添加一些相关的 RAG 示例到提示中进行上下文内学习来从管道中挤出更多性能。

#### RAG + 微调

我们的最终优化从训练集和验证集之外添加了 1000 个示例，这些示例被嵌入并放置在向量数据库中。然后我们使用 gpt-4 微调模型进行了进一步测试，结果可能有些出人意料：

![Icelandic case study diagram](https://cdn.openai.com/API/docs/images/diagram-optimizing-accuracy-07.png) _每种调优方法的 Bleu 分数（满分 100）_

RAG 实际上**降低了**准确性，从我们的 GPT-4 微调模型下降了四分到 83。

这说明了一个观点：你要为正确的工作使用正确的优化工具——每种工具都提供了我们通过评估和迭代变更来管理的好处和风险。我们在评估中观察到的行为以及我们对这个问题的了解告诉我们，这是一个行为优化问题，额外的上下文不一定会帮助模型。这在实践中得到了验证——RAG 实际上通过给模型额外的噪音来混淆它，而它已经通过微调有效地学会了这个任务。

我们现在有了一个应该接近生产就绪的模型，如果我们想进一步优化，可以考虑更广泛多样性和数量的训练示例。

现在你应该对 RAG 和微调有了认识，以及何时使用每种方法是合适的。关于这些工具，你最后应该了解的是，一旦引入它们，我们的迭代速度就会有一个权衡：

*   对于 RAG，你需要调整检索以及 LLM 行为
*   对于微调，你需要在进行额外调整时重新运行微调过程并管理你的训练集和验证集。

这两者都可能是耗时且复杂的过程，随着你的 LLM 应用变得更加复杂，可能会引入回归问题。如果你从本文中只记住一件事，那就是在使用更复杂的 RAG 或微调之前，尽可能从基本方法中挤出尽可能多的准确性——让你的准确性目标成为目的，而不是因为 RAG + FT 被认为是最复杂的就去追求它们。

## 对于生产环境来说多少准确性是"足够好"的

调整 LLM 的准确性可能是一场永无止境的战斗——使用现成的方法它们不太可能达到 99.999% 的准确性。本节是关于决定何时准确性足够——你如何放心地将 LLM 投入生产，以及如何管理你推出的解决方案的风险。

我发现从**业务**和**技术**两个角度来思考这个问题很有帮助。我将描述管理两者的高层方法，并使用客户服务帮助台用例来说明我们如何在两种情况下管理风险。

### 业务

对于业务来说，在经历了基于规则或传统机器学习系统，甚至是人类的相对确定性之后，信任 LLM 可能很困难！一个失败是开放式且不可预测的系统是一个难以解决的问题。

我看到一种成功的方法是针对客户服务用例——为此，我们做了以下事情：

首先我们识别主要的成功和失败案例，并为它们分配估计成本。这给了我们一个清晰的表述，说明基于试点性能，该解决方案可能节省或花费多少。

*   例如，一个之前由人工解决的案例被 AI 解决可能节省 **$20**。
*   一个不应该被升级到人工的案例被升级可能花费 **$40**
*   在最坏的情况下，客户对 AI 感到非常沮丧以至于流失，花费我们 **$1000**。我们假设这在 5% 的情况下发生。

| 事件 | 价值 | 案例数量 | 总价值 |
| --- | --- | --- | --- |
| AI 成功 | +20 | 815 | $16,300 |
| AI 失败（升级） | \-40 | 175.75 | $7,030 |
| AI 失败（流失） | \-1000 | 9.25 | $9,250 |
| **结果** |  |  | **+20** |
| **盈亏平衡准确率** |  |  | **81.5%** |

我们做的另一件事是衡量围绕流程的经验统计数据，这将帮助我们衡量解决方案的宏观影响。再次以客户服务为例，这些可能是：

*   纯人工交互与 AI 交互的 CSAT 分数
*   回顾性审查案例中人工与 AI 的决策准确性
*   人工与 AI 的解决时间

在客户服务示例中，这帮助我们在几次试点获得清晰数据后做出了两个关键决定：

1.  即使我们的 LLM 解决方案比我们想要的更多地升级到人工，它仍然比现有解决方案节省了巨大的运营成本。这意味着即使 85% 的准确率也可以接受，如果那 15% 主要是早期升级的话。
2.  在失败成本非常高的地方，例如欺诈案例被错误解决，我们决定由人工主导，AI 作为助手。在这种情况下，决策准确性统计帮助我们做出了我们不放心完全自主的判断。

### 技术

在技术方面更加明确——现在业务已经清楚了他们期望的价值和可能出错的成本，你的角色是构建一个优雅处理失败的解决方案，不会破坏用户体验。

让我们再次使用客户服务示例来说明这一点，我们假设我们有一个在确定意图方面准确率为 85% 的模型。作为技术团队，以下是我们可以最小化不正确的 15% 影响的几种方式：

*   我们可以通过提示工程让模型在不确信时提示客户提供更多信息，这样我们的首次准确率可能会下降，但给予 2 次确定意图的机会后可能更准确。
*   我们可以给二线助手选项将案例传回意图确定阶段，再次给用户体验一种自我修复的方式，代价是一些额外的用户延迟。
*   我们可以通过提示工程让模型在意图不明确时转交给人工，这在短期内会花费我们一些运营节省，但从长远来看可能抵消客户流失风险。

这些决定然后反馈到我们的用户体验中，它以更高准确性为代价变慢，或者更多的人工干预，这些反馈到上面业务部分涵盖的成本模型中。

你现在有了一种方法来分解设定准确性目标所涉及的业务和技术决策，该目标基于业务现实。
