模型提示词通常包含重复内容，例如系统提示词和常见指令。OpenAI 会将 API 请求路由到最近处理过相同提示词的服务器，使其比从头处理提示词更便宜、更快速。提示词缓存可以将延迟降低多达 80%，将输入 token 成本降低多达 90%。提示词缓存会自动应用于所有 API 请求（无需更改代码），且不会产生额外费用。提示词缓存适用于所有最新[模型](/api/docs/models)，gpt-4o 及更新版本。

本指南详细介绍了提示词缓存的工作原理，以便您优化提示词以降低延迟和成本。

## 构建提示词结构

缓存命中仅在提示词的精确前缀匹配时才可能发生。为了实现缓存收益，请将静态内容（如指令和示例）放在提示词的开头，将可变内容（如用户特定信息）放在末尾。这同样适用于图像和工具，它们在请求之间必须完全相同。

## 工作原理

对于 1024 个 token 或更长的提示词，缓存会自动启用。当您发起 API 请求时，会发生以下步骤：

1.  **缓存路由**：

*   请求根据提示词初始前缀的哈希值路由到某台机器。哈希通常使用前 256 个 token，但确切长度因模型而异。
*   如果您提供了 [`prompt_cache_key`](/api/docs/api-reference/responses/create#responses-create-prompt_cache_key) 参数，它会与前缀哈希组合，允许您影响路由并提高缓存命中率。当许多请求共享较长的公共前缀时，这尤其有益。
*   如果相同前缀和 `prompt_cache_key` 组合的请求超过一定速率（大约每分钟 15 个请求），部分请求可能会溢出并路由到其他机器，从而降低缓存效果。

2.  **缓存查找**：系统检查您提示词的初始部分（前缀）是否存在于所选机器的缓存中。
3.  **缓存命中**：如果找到匹配的前缀，系统将使用缓存的结果。这会显著降低延迟并减少成本。
4.  **缓存未命中**：如果未找到匹配的前缀，系统将处理您的完整提示词，并在该机器上缓存前缀以供未来请求使用。

## 提示词缓存保留

提示词缓存可以使用内存保留或扩展保留策略。当可用时，扩展提示词缓存旨在更长时间地保留缓存，以便后续请求更有可能命中缓存。

两种保留策略的提示词缓存定价相同。

要配置提示词缓存保留策略，请在 `Responses.create` 请求（或使用 Chat Completions 时的 `chat.completions.create`）中设置 `prompt_cache_retention` 参数。

### 内存提示词缓存保留

内存提示词缓存保留适用于所有支持提示词缓存的模型，但 `gpt-5.5`、`gpt-5.5-pro` 和所有未来模型除外。

使用内存策略时，缓存的前缀通常在 5 到 10 分钟不活动后保持有效，最长可达一小时。内存缓存的前缀仅保存在易失性 GPU 内存中。

### 扩展提示词缓存保留

扩展提示词缓存保留适用于以下模型：

*   gpt-5.5
*   gpt-5.5-pro
*   gpt-5.4
*   gpt-5.2
*   gpt-5.1-codex-max
*   gpt-5.1
*   gpt-5.1-codex
*   gpt-5.1-codex-mini
*   gpt-5.1-chat-latest
*   gpt-5
*   gpt-5-codex
*   gpt-4.1

扩展提示词缓存保留使缓存的前缀保持更长时间的活动状态，最长可达 24 小时。扩展提示词缓存通过在内存满时将 key/value 张量卸载到 GPU 本地存储来工作，显著增加了可用于缓存的存储容量。

key/value 张量是模型注意力层在预填充期间产生的中间表示。只有 key/value 张量可以持久化到本地存储；原始客户内容（如提示词文本）仅保留在内存中。

### 按请求配置

如果您未指定保留策略，对于大多数模型，默认值为 `in_memory`。对于 `gpt-5.5`、`gpt-5.5-pro` 和所有未来模型，默认值为 `24h`，且不支持 `in_memory`。允许的值为 `in_memory` 和 `24h`。

```
{
  "model": "gpt-5.5",
  "input": "Your prompt goes here...",
  "prompt_cache_retention": "24h"
}
```

## 要求

缓存适用于包含 1024 个或更多 token 的提示词。

所有请求（包括少于 1024 个 token 的请求）都会在 `usage.prompt_tokens_details` [Response 对象](/api/docs/api-reference/responses/object)或 [Chat 对象](/api/docs/api-reference/chat/object)中显示 `cached_tokens` 字段，指示有多少提示词 token 命中了缓存。对于少于 1024 个 token 的请求，`cached_tokens` 将为零。

```
"usage": {
  "prompt_tokens": 2006,
  "completion_tokens": 300,
  "total_tokens": 2306,
  "prompt_tokens_details": {
    "cached_tokens": 1920
  },
  "completion_tokens_details": {
    "reasoning_tokens": 0,
    "accepted_prediction_tokens": 0,
    "rejected_prediction_tokens": 0
  }
}
```

### 可缓存的内容

*   **消息：** 完整的消息数组，包括系统、用户和助手交互。
*   **图像：** 用户消息中包含的图像，无论是链接还是 base64 编码数据，以及可以发送多张图像。确保 detail 参数设置相同，因为它会影响图像的 token 化。
*   **工具使用：** 消息数组和可用 `tools` 列表都可以被缓存，它们都计入最低 1024 token 的要求。
*   **结构化输出：** 结构化输出 schema 作为系统消息的前缀，可以被缓存。

## 最佳实践

*   将提示词结构化为**静态或重复内容在开头**，动态的用户特定内容在末尾。
*   在共享公共前缀的请求中一致使用 **[`prompt_cache_key`](/api/docs/api-reference/responses/create#responses-create-prompt_cache_key) 参数**。选择适当的粒度，使每个唯一的前缀-`prompt_cache_key` 组合保持在每分钟 15 个请求以下，以避免缓存溢出。
*   **监控您的缓存性能指标**，包括缓存命中率、延迟和缓存 token 的比例，以优化您的策略。您可以通过记录如上所示的 usage 字段结果来监控缓存 token 计数，或在 OpenAI Usage 仪表板中查看。
*   **保持具有相同提示词前缀的稳定请求流**，以最大限度地减少缓存驱逐并最大化缓存收益。

## 常见问题

1.  **缓存如何维护数据隐私？**
    
    提示词缓存不会在组织之间共享。只有同一组织的成员才能访问相同提示词的缓存。使用扩展提示词缓存时，key/value 张量的最大保留期为 24 小时。
    
2.  **提示词缓存是否会影响输出 token 生成或 API 的最终响应？**
    
    提示词缓存不会影响输出 token 的生成或 API 提供的最终响应。无论是否使用缓存，生成的输出都是相同的。这是因为只有提示词本身被缓存，而实际响应每次都是基于缓存的提示词重新计算的。
    
3.  **是否有手动清除缓存的方法？**
    
    目前不支持手动清除缓存。最近未被访问的提示词会自动从缓存中清除。典型的缓存驱逐发生在 5-10 分钟不活动后，但在非高峰期有时可持续最长一小时。
    
4.  **使用提示词缓存是否需要额外付费？**
    
    不需要。缓存自动发生，无需显式操作，也无需为使用缓存功能支付额外费用。
    
5.  **缓存的提示词是否计入 TPM 速率限制？**
    
    是的，缓存不会影响速率限制。
    
6.  **提示词缓存是否适用于零数据保留请求？**
    
    内存缓存保留不会将任何数据保存到磁盘。扩展提示词缓存可能会将 key/value 张量存储在 GPU 本地存储中，而 key-value 张量源自客户内容。此数据不会在缓存过期后保留——key-value 张量保留 1-2 小时（大多数使用情况），最多 24 小时。如果您的项目启用了零数据保留，扩展提示词缓存请求不会被阻止。其他零数据保留仍然适用，例如从滥用日志中排除客户内容以及阻止使用 `store=True`。有关零数据保留的更多信息，请参阅[您的数据](/api/docs/guides/your-data)指南。
    
7.  **提示词缓存是否适用于数据驻留？**
    
    内存提示词缓存不存储数据，因此不影响数据驻留。
    
    扩展缓存临时将数据存储在 GPU 机器上，使用区域推理时仅保留在区域内。
