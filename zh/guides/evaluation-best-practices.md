# Best practices

> Learn best practices for designing evals to test model performance in production environments.

生成式 AI 具有可变性。模型有时会对相同的输入产生不同的输出，这使得传统的软件测试方法不足以应对 AI 架构。评估（**evals**）是一种在这种可变性下测试 AI 系统的方法。

本指南提供了设计评估的高层指导。要开始使用 [Evals API]( https://developers.openai.com/api/reference/evals)，请参阅[评估模型性能](/guides/evals)。

## 什么是评估？

评估是用于衡量模型性能的结构化测试。它们有助于确保准确性、性能和可靠性，尽管 AI 系统具有非确定性特征。它们也是_提升_基于 LLM 的应用性能的少数方法之一（通过[微调](/guides/model-optimization)）。

### 评估的类型

当你看到"evals"这个词时，它可能指以下几种含义：

*   用于孤立比较模型的行业基准测试，如 [MMLU](https://github.com/openai/evals/blob/main/examples/mmlu.ipynb) 和 [HuggingFace 排行榜](https://huggingface.co/collections/open-llm-leaderboard/the-big-benchmarks-collection-64faca6335a7fc7d4ffe974a)上列出的基准
*   标准数值分数——如 [ROUGE](https://aclanthology.org/W04-1013/)、[BERTScore](https://arxiv.org/abs/1904.09675)——你可以在为自己的用例设计评估时使用
*   你为衡量 LLM 应用性能而实施的特定测试

本指南讨论的是第三种类型：设计你自己的评估。

### 如何解读评估

你经常会看到 0 到 1 之间的数值评估分数。评估不仅仅是分数。将指标与人工判断相结合，确保你在回答正确的问题。

**评估技巧**

  

*   采用评估驱动开发：尽早且频繁地评估。在每个阶段编写有针对性的测试。
*   设计特定任务的评估：使测试反映模型在真实世界分布中的能力。
*   记录一切：在开发过程中记录日志，以便从日志中挖掘好的评估案例。
*   尽可能自动化：构建评估结构以允许自动化评分。
*   这是一段旅程，而非终点：评估是一个持续的过程。
*   保持一致性：使用人工反馈来校准自动化评分。

**反模式**

  

*   过于通用的指标：仅依赖学术指标如困惑度或 BLEU 分数。
*   有偏差的设计：创建不能忠实再现生产流量模式的评估数据集。
*   凭感觉的评估：使用"看起来好像在工作"作为评估策略，或者等到上线后才实施任何评估。
*   忽视人工反馈：不将自动化指标与人工评估进行校准。

## 设计你的评估流程

评估工作流有几个重要组成部分：

1.  **定义评估目标**。评估的成功标准是什么？
2.  **收集数据集**。哪些数据将帮助你根据目标进行评估？考虑合成评估数据、领域特定评估数据、购买的评估数据、人工策划的评估数据、生产数据和历史数据。
3.  **定义评估指标**。你将如何检查成功标准是否满足？
4.  **运行和比较评估**。迭代并改进模型在你的任务或系统中的性能。
5.  **持续评估**。设置持续评估（CE）以在每次变更时运行评估，监控你的应用以识别新的非确定性案例，并随时间增长评估集。

让我们通过几个示例来说明。

### 示例：摘要转录

要测试你的基于 LLM 的应用摘要转录的能力，你的评估设计可能是：

1.  **定义评估目标**  
    模型应该能够在相关性和准确性方面与参考摘要竞争。
2.  **收集数据集**  
    使用生产数据（从用户对生成摘要的反馈中收集）和由领域专家（作者）创建的数据集的混合来确定"好的"摘要。
3.  **定义评估指标**  
    在 1000 个保留的参考转录→摘要集上，实现至少 0.40 的 ROUGE-L 分数和使用 G-Eval 至少 80% 的连贯性分数。
4.  **运行和比较评估**  
    使用 [Evals API](/guides/evals) 在 OpenAI 仪表板中创建和运行评估。
5.  **持续评估**  
    设置持续评估（CE）以在每次变更时运行评估，监控你的应用以识别新的非确定性案例，并随时间增长评估集。

LLM 更擅长在选项之间进行区分。因此，评估应该关注成对比较、分类或根据特定标准评分等任务，而不是开放式生成。将评估方法与 LLM 在比较方面的优势对齐，可以更可靠地评估 LLM 输出或模型比较。

### 示例：文档问答

要测试你的基于 LLM 的应用进行文档问答的能力，你的评估设计可能是：

1.  **定义评估目标**  
    模型应该能够提供精确的答案，根据需要回忆上下文来推理用户提示，并提供满足用户需求的答案。
2.  **收集数据集**  
    使用生产数据（从用户对其问题所得答案的满意度中收集）、由领域专家创建的问题的硬编码正确答案以及来自日志的历史数据的混合。
3.  **定义评估指标**  
    上下文召回率至少 0.85，上下文精确率超过 0.7，以及 70% 以上的正面评价答案。
4.  **运行和比较评估**  
    使用 [Evals API](/guides/evals) 在 OpenAI 仪表板中创建和运行评估。
5.  **持续评估**  
    设置持续评估（CE）以在每次变更时运行评估，监控你的应用以识别新的非确定性案例，并随时间增长评估集。

在创建评估数据集时，o3 和 GPT-4.1 对于收集评估示例和边缘案例很有用。考虑使用 o3 帮助你生成跨各种场景的多样化测试数据。确保你的测试数据包括典型案例、边缘案例和对抗性案例。使用人工专家标注员。

## 确定你需要评估的位置

随着从简单架构到更复杂架构的过渡，复杂性会增加。以下是四种常见的架构模式：

*   [单轮模型交互](#single-turn-model-interactions)
*   [工作流](#workflow-architectures)
*   [单智能体](#single-agent-architectures)
*   [多智能体](#multi-agent-architectures)

阅读下面每种架构的内容，以确定非确定性在你的系统中出现的位置。那就是你需要实施评估的地方。

### 单轮模型交互

在这种架构中，用户向模型提供输入，模型处理这些输入（连同提供的任何开发者提示）以生成相应的输出。

#### 示例

以在线零售场景为例。你的系统提示指示模型将客户的问题**分类**为以下类别之一：

*   `order_status`
*   `return_policy`
*   `technical_issue`
*   `cancel_order`
*   `other`

为确保一致、高效的用户体验，模型应该**只返回与用户意图匹配的标签**。假设客户问："我的订单状态是什么？"

| 引入的非确定性 | 对应的评估领域 | 示例评估问题 |
| --- | --- | --- |
| 开发者和用户提供的输入 | **指令遵循**：模型是否准确理解并按照提供的指令行事？  
  
**指令遵循**：模型是否优先考虑系统提示而非冲突的用户提示？ | 模型是否专注于分类任务还是被用户的问题带偏？ |
| 模型生成的输出 | **功能正确性**：模型的输出是否足够准确、相关和全面，以完成预期的任务或目标？ | 模型对意图的判断是否正确匹配预期意图？ |

### 工作流架构

当你需要解决更复杂的问题时，你可能会从单轮模型交互过渡到将多个模型调用链接在一起的多步骤工作流。工作流不会引入任何新的非确定性元素，但它们涉及多个底层模型交互，你可以单独评估这些交互。

#### 示例

以与之前相同的示例为例，客户询问其订单状态。工作流架构对客户请求进行分类，并通过逐步流程进行路由：

1.  提取订单 ID
2.  查找订单详情
3.  将订单详情提供给模型以生成最终响应

此工作流中的每个步骤都有自己的系统提示，模型必须遵循该提示，将所有获取的数据整理成友好的输出。

| 引入的非确定性 | 对应的评估领域 | 示例评估问题 |
| --- | --- | --- |
| 开发者和用户提供的输入 | **指令遵循**：模型是否准确理解并按照提供的指令行事？  
  
**指令遵循**：模型是否优先考虑系统提示而非冲突的用户提示？ | 模型是否专注于分类任务还是被用户的问题带偏？  
  
模型是否遵循指令尝试提取订单 ID？  
  
最终响应是否包含订单状态、预计到达日期和跟踪号？ |
| 模型生成的输出 | **功能正确性**：模型的输出是否足够准确、相关和全面，以完成预期的任务或目标？ | 模型对意图的判断是否正确匹配预期意图？  
  
最终响应是否包含正确的订单状态、预计到达日期和跟踪号？ |

### 单智能体架构

与工作流不同，智能体解决的是需要灵活决策的非结构化问题。智能体有指令和一组工具，并动态选择使用哪个工具。这引入了新的非确定性机会。

工具是开发者定义的代码块，模型可以执行这些代码。这可以从小型辅助函数到现有服务的 API 调用。例如，`check_order_status(order_id)` 可以是一个工具，它接受参数 `order_id` 并调用 API 来检查订单状态。

#### 示例

让我们将客户服务示例改编为使用单个智能体。该智能体可以访问三个不同的工具：

*   订单查询工具
*   密码重置工具
*   产品常见问题工具

当客户询问其订单状态时，智能体动态决定是调用工具还是回复客户。例如，如果客户问"我的订单状态是什么？"，智能体现在可以跟进请求客户提供订单 ID。这有助于创造更自然的用户体验。

| 非确定性 | 对应的评估领域 | 示例评估问题 |
| --- | --- | --- |
| 开发者和用户提供的输入 | **指令遵循**：模型是否准确理解并按照提供的指令行事？  
  
**指令遵循**：模型是否优先考虑系统提示而非冲突的用户提示？ | 模型是否专注于分类任务还是被用户的问题带偏？  
  
模型是否遵循指令尝试提取订单 ID？ |
| 模型生成的输出 | **功能正确性**：模型的输出是否足够准确、相关和全面，以完成预期的任务或目标？ | 模型对意图的判断是否正确匹配预期意图？ |
| 模型选择的工具 | **工具选择**：测试智能体是否能够选择正确工具的评估。  
  
**数据精确性**：验证智能体是否使用正确参数调用工具的评估。通常这些参数是从对话历史中提取的，因此目标是验证此提取是否正确。 | 当用户询问其订单状态时，模型是否正确推荐调用订单查询工具？  
  
模型是否正确提取用户提供的订单 ID 传递给查询工具？ |

### 多智能体架构

当你向单智能体架构添加工具和任务时，模型可能难以遵循指令或选择正确的工具来调用。多智能体架构通过创建多个专注于不同领域的独立智能体来帮助解决这个问题。多个智能体之间的分类和交接引入了新的非确定性机会。

使用多智能体架构的决定应该由你的评估驱动。从多智能体架构开始会增加不必要的复杂性，可能会减慢你的上线时间。

#### 示例

将单智能体示例拆分为多智能体架构，我们将有四个不同的智能体：

1.  分类智能体
2.  订单智能体
3.  账户管理智能体
4.  销售智能体

当客户询问其订单状态时，分类智能体可能会将对话交接给订单智能体来查询订单。如果客户改变话题询问产品，订单智能体应该将请求交回给分类智能体，然后分类智能体交接给销售智能体来获取产品信息。

| 非确定性 | 对应的评估领域 | 示例评估问题 |
| --- | --- | --- |
| 开发者和用户提供的输入 | **指令遵循**：模型是否准确理解并按照提供的指令行事？  
  
**指令遵循**：模型是否优先考虑系统提示而非冲突的用户提示？ | 模型是否专注于分类任务还是被用户的问题带偏？  
  
假设 `lookup_order` 调用已返回，订单智能体是否返回了跟踪号和交付日期（不一定要是正确的）？ |
| 模型生成的输出 | **功能正确性**：模型的输出是否足够准确、相关和全面，以完成预期的任务或目标？ | 模型对意图的判断是否正确匹配预期意图？  
  
假设 `lookup_order` 调用已返回，订单智能体是否在其响应中提供了正确的跟踪号和交付日期？  
  
订单智能体是否遵循系统指令，在处理退货之前询问客户请求退货的原因？ |
| 模型选择的工具 | **工具选择**：测试智能体是否能够选择正确工具的评估。  
  
**数据精确性**：验证智能体是否使用正确参数调用工具的评估。通常这些参数是从对话历史中提取的，因此目标是验证此提取是否正确。 | 订单智能体是否正确调用了订单查询工具？  
  
订单智能体是否正确调用了 `refund_order` 工具？  
  
订单智能体是否使用正确的订单 ID 调用了订单查询工具？  
  
账户智能体是否使用正确的账户 ID 正确调用了 `reset_password` 工具？ |
| 智能体交接 | **智能体交接准确性**：测试每个智能体是否能够适当识别分类到另一个智能体的决策边界的评估 | 当用户询问订单状态时，分类智能体是否正确传递给订单智能体？  
  
当用户改变话题谈论最新产品时，订单智能体是否将控制权交回给分类智能体？ |

## 创建和组合不同类型的评估器

在设计你自己的评估时，有几种特定的评估器类型可供选择。另一种思考方式是你希望评估器扮演什么角色。

### 基于指标的评估

定量评估提供数值分数，你可以用来过滤和排名结果。它们为自动化回归测试提供有用的基准。

*   **示例**：精确匹配、字符串匹配、ROUGE/BLEU 评分、函数调用准确性、可执行评估（通过执行来评估功能或行为——例如 text2sql）
*   **挑战**：可能不适合特定用例，可能遗漏细微差别

### 人工评估

人工判断评估提供最高质量，但速度慢且成本高。

*   **示例**：浏览系统输出以了解它们看起来是更好还是更差；创建随机化、盲测的测试，让员工、承包商或外包标注机构判断系统输出的质量（例如，对一小组可能的输出进行排名，或给每个输出 1-5 的评分）
*   **挑战**：人工专家之间的分歧、成本高、速度慢
*   **建议**：
    *   进行多轮详细的人工审查以完善评分卡
    *   实施"展示而非告知"策略，提供不同分数级别的示例（例如，10 分中的 1 分、3 分和 8 分）
    *   除数值分数外，还包括通过/失败阈值
    *   聚合多个审查者的简单方法是采用共识投票

### LLM 作为评判者和模型评分器

使用模型来评判输出比人工评估运行成本更低且更具可扩展性。强大的 LLM 评判者如 GPT-4.1 可以匹配受控和众包的人类偏好，达到超过 80% 的一致率（与人类之间的一致率相同）。

*   **示例**：
    *   成对比较：向评判模型展示两个响应，并要求它根据特定标准确定哪个更好
    *   单答案评分：评判模型单独评估一个响应，根据预定义的质量指标分配分数或评级
    *   参考引导评分：向评判模型提供参考或"黄金标准"答案，作为评估给定响应的基准
*   **挑战**：位置偏差（响应顺序）、冗长偏差（偏好更长的响应）
*   **建议**：
    *   使用成对比较或通过/失败以获得更高可靠性
    *   如果可以的话，使用最强大的模型进行评分（例如 o3）——o 系列模型擅长根据评分标准或参考专家答案集合进行自动评分
    *   控制响应长度，因为 LLM 通常偏向更长的响应
    *   添加推理和思维链，因为评分前的推理可以提高评估性能
    *   一旦 LLM 评判者达到更快、更便宜且与人工标注一致的程度，就扩大规模
    *   构建问题结构以允许自动化评分，同时保持任务的完整性——一种常见方法是将问题重新格式化为多选题格式
    *   确保评估标准清晰且详细

没有完美的策略。LLM 作为评判者的质量因问题上下文而异，而使用专家人工标注员提供真实标签既昂贵又耗时。

## 处理边缘案例

虽然你的评估应该覆盖每种架构的主要、正常路径场景，但现实世界的 AI 系统经常遇到挑战系统性能的边缘案例。评估这些边缘案例对于确保可靠性和良好的用户体验非常重要。

我们看到这些边缘案例分为几类：

### 输入可变性

因为用户向模型提供输入，我们的系统必须灵活处理用户可能交互的不同方式，例如：

*   非英语或多语言输入
*   输入文本以外的格式（例如 XML、JSON、Markdown、CSV）
*   输入模态（例如图像）

你的指令遵循和功能正确性评估需要适应用户可能尝试的输入。

### 上下文复杂性

许多基于 LLM 的应用由于对请求上下文的理解不足而失败。这种上下文可能来自用户或过去对话历史中的噪声。

示例包括：

*   单个请求中的多个问题或意图
*   拼写错误和拼写失误
*   上下文最少的简短请求（例如，如果用户只说："退货"）
*   长上下文或长时间运行的对话
*   返回具有模糊属性名称的数据的工具调用（例如 `"on: 123"`，其中"on"是订单号）
*   多次工具调用，有时导致不正确的参数
*   多次智能体交接，有时导致循环交接

### 个性化和定制

虽然 AI 通过适应用户特定请求来改善用户体验，但这种灵活性引入了许多边缘案例。为你想要特别支持和阻止的用例明确定义评估：

*   越狱尝试，试图让模型做不同的事情
*   格式化请求（例如，格式化为 JSON，或使用项目符号）
*   用户提示与你的系统提示冲突的情况
